FAQ & troubleshooting

Direct answers to operational, security, and deployment questions, plus fixes for common client and bridge errors.

Frequently asked questions

Does a Hogman pen patch vulnerabilities in our equipment?
No. A pen removes equipment controllers and internal dashboards from the open internet and restricts reachability to invited pen members, which eliminates drive-by scanning and external opportunistic attacks. It does not patch device firmware or fix bugs inside web apps. Keep vendor security updates enabled and replace default device passwords.
Can an equipment controller that can't install software join a pen?
Yes — keep the controller strictly on your local LAN with no router port-forwarding, and run hogman-join share on a small always-on Linux or Mac computer (such as a Raspberry Pi or mini PC) on the same local network. The local upstream can speak plain HTTP while staff always connect over standard HTTPS (:443). See Dedicated on-site bridge setup.
Should all of our locations share one pen?
For multi-site operations, no. Create a separate pen per region or store group (for example, region-north and region-south) so a single lost laptop or compromised contractor account cannot reach every facility.
How should we manage outside contractors and service vendors?
Create a single-use invite link in the specific site pen they service and tag it with their name and work order. When the visit ends, press Suspend (~2 s, reversible for recurring vendors) or Remove (~2 s, permanent, retires their handle and site names). See Suspending and offboarding.
Why not just use a corporate VPN or Tailscale?
Traditional VPNs route ordinary browsing through a central gateway and often expose whole LAN subnets by default. Tailscale is excellent for personal and engineering meshes — Hogman is built on Tailscale's open-source tsnet and runs cleanly alongside it. Hogman is purpose-built for small teams and operations that need zero-IT browser access to specific web panels: single-use invite links, HTTPS-only (:443) to explicitly shared servers, standard public HTTPS certificates without a custom root CA, and a built-in web portal for ~2 s revocation.
Can we self-host a Hogman pen control plane?
Hogman runs pen control planes hosted-only on hogman.network (we do not support self-hosted pen servers or custom pen domains). Your equipment, bridges, and internal web apps stay on your own machines over end-to-end encrypted WireGuard. The entire codebase is AGPL-3.0 on GitHub with SLSA-attested releases (gh attestation verify hogman-join --repo celtiberi/hogman), and teams can read the operator guide to inspect how the hosted platform runs.
What does Hogman deliberately not do?
Anything other than HTTPS (port 443) to explicitly shared server nodes. There is no SSH, no raw TCP/UDP (such as raw Modbus, BACnet, or RDP without a web UI), no exit nodes, no LAN subnet routing, and zero inbound connections to staff laptops. Every extra protocol expands attack surface on employee machines, so there is no toggle to enable them.
Can internet scanners, bots, or AI crawlers find our bridged devices?
No. Pen hostnames have zero public A/AAAA records (ns1.hogman.network returns empty NODATA except for temporary ACME challenge tokens), and mesh IPs are not routable from the public internet. Hogman adds zero ads, trackers, or analytics anywhere. What a pen cannot prevent: an authorized user screenshotting or exporting data, an internal app phoning home on its own, or site hostnames appearing in public Certificate Transparency logs (names only — never site contents or IPs).
Can Hogman or a pen owner read our internal traffic?
Not passively. Traffic between staff browsers and bridged servers is encrypted end to end with WireGuard + inner TLS 1.3. Owners and the hosted control plane can see membership, enrolled devices, and mesh DNS lookups, and control admission/DNS-01 — see the full threat model.
Can a manager belong to multiple site pens?
Yes — join each site pen with its own invite link. Local proxies run side by side and share one combined proxy.pac. Until pens.hogman.network is listed on the Public Suffix List, use a separate browser profile for any pen you do not fully trust so cookies remain isolated.
What if an employee loses a laptop?
An owner or admin should immediately suspend or remove the account (or the employee can remove the lost laptop under Your devices from another enrolled workstation) — pen credentials live in user-readable state files on disk. If someone loses every enrolled device, there is no account recovery and no support backdoor: issue a fresh invite, restore their role, and remove the old account. Always appoint a second owner on every production pen.
Platform support, pricing, and security audit status?
Hogman is currently an invite-only testbed while commercial plans are prepared. macOS and Linux work today; Windows is built but untested, and mobile apps are in progress. The software is open source (AGPL-3.0) and has not yet had an independent security audit — evaluate carefully before relying on it for safety-critical systems.

Troubleshooting

Pen dashboards say "DNS address could not be found" while a corporate VPN is active
On macOS, Network Extension VPNs (corporate VPNs, WireGuard, ProtonVPN, Mullvad) override the system automatic proxy setting while connected, causing browsers to fall back to public DNS — where pen hostnames intentionally do not exist. The hogman-join connection is still up. Pause the VPN while checking pen dashboards, or set Firefox's built-in Automatic proxy configuration URL to the address printed by hogman-join so pen names route to hogman-join while ordinary traffic stays on the VPN. (A companion browser extension for Chrome, Brave, Edge, and Firefox is in browser-ext/ for manual developer install while store listings are prepared.)
The browser can't find pen sites (no VPN running)
Only applications using the pen's local proxy can resolve pen names. On macOS, hogman-join sets the automatic proxy URL automatically unless another non-Hogman proxy is already configured (in which case it prints the URL to set manually). On Linux, point the browser's automatic proxy setting to the printed http://127.0.0.1:<port>/proxy.pac URL and reload proxy settings after joining or leaving a pen. For CLI tools, see Browsers and command-line tools.
"This computer cannot find the network's names yet"
Run the same join command again. The invite already enrolled this workstation, so the rerun skips invite redemption and finishes verifying the portal. (That invite will not work on a second computer — use Add a device instead.)
The setup tool tried to open a browser on a headless bridge server
Pass --no-open. The portal URL is still printed to the terminal.
"is already being shared from this computer"
That bridge is already running in the background or another terminal. Inspect active bridges with ~/hogman-join share list and stop one with ~/hogman-join share stop NAME.
A bridged dashboard says "the app isn't answering right now"
The Hogman bridge node is up, but the local controller or web app is unreachable at the configured LAN address or port. Verify the equipment is powered on and reachable from the bridge machine (for example, curl -I http://192.168.1.40) and reload.
"the invite was not accepted"
Member invites work once and expire after 7 days; personal device links and server share links expire after 1 hour. Issue a fresh link from the portal.
A workstation ran leave and needs access again
leave removes the device, not the person's membership. Generate a 1-hour device link from another enrolled device (or ask an owner/admin for a fresh invite if no devices remain) and rejoin.
"this link is from an older release (carries fp=)"
Links from early private-CA test builds (before public certificates) are rejected. Issue a fresh link; pre-switchover .hogman pens must be recreated.

Still stuck? Open an issue on GitHub with the command you ran and the exact output.
