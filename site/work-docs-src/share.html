Bridging equipment & apps

Keep refrigeration controllers, HVAC/BMS panels, cameras, and internal web apps strictly on your local network, and bridge only their web interfaces into a pen over standard HTTPS (port 443).

$ ~/hogman-join share cooler-1 http://192.168.1.40 --background

• Adding a server for cooler-1.store-north.pens.hogman.network (ops-north)
• Proxying http://192.168.1.40 as https://cooler-1.store-north.pens.hogman.network

✓ https://cooler-1.store-north.pens.hogman.network is up.
  Everyone in the pen can open it.
  Take it down and free the name: hogman-join share stop cooler-1

What you can bridge

TargetCommandBehavior
On-site LAN equipment share cooler-1 http://192.168.1.40 Bridges a local controller, HVAC/BMS panel, camera NVR, or NAS web UI into the pen over HTTPS with zero open router ports. The local device can speak plain HTTP while staff always connect over HTTPS (:443).
Internal web application share inventory 8080 Reverse-proxies http://127.0.0.1:8080 over HTTPS (WebSockets supported; forwards X-Forwarded-For, -Host, and -Proto while preserving the upstream Host header).
Static manuals or reports share sops ~/site-manuals Serves index.html (or a directory listing) over HTTPS inside Go's os.Root sandbox with no symlink escape.

Already running Caddy or nginx on site with multiple internal apps behind it? Bridge its local port (share ops 8080) and let Hogman handle the private hostname and TLS.

Dedicated on-site bridge setup

Equipment controllers cannot install client software themselves. Keep them on your local LAN and place a small always-on Linux or Mac computer (such as a Raspberry Pi 4/5 or mini PC) on the same network. The bridge machine does not need to enroll as a personal member device:

  1. Close public router ports: remove any public IP mapping or router port-forwarding pointing at the controller. Verify its web panel answers only on the local LAN (for example, http://192.168.1.40).
  2. Generate a share link: on your pen's management portal, press Get a share link and copy the single-use server link (valid for 1 hour). Always use a share link for bridges and servers — not a member invite link.
  3. Start the bridge in the background: download hogman-join on the bridge box (Raspberry Pi 4/5 uses hogman-join-Linux-aarch64) and pass the share link with --background: 
    $ ./hogman-join share cooler-1 http://192.168.1.40 'https://store-north.gate.hogman.network/join#k=…' --background
  4. Enable boot startup on headless Linux: on macOS (launchd) and Linux (systemd user services), --background installs a login service automatically. On a headless Linux bridge where nobody logs in after a power cycle, run once: 
    $ sudo loginctl enable-linger $USER
    Pass --no-service only if you want a temporary background process until reboot. (Windows is built but untested and does not yet register a reboot service.)

You can run multiple share commands from the same on-site bridge machine — for example, one for cooler-1 and one for hvac-main — and each gets its own isolated server identity and hostname. Nothing else on your LAN is exposed.

Multi-site separation and naming

  • Separate pens per site or region: put distinct store groups or facilities in separate pens (e.g. region-north.pens.hogman.network and region-south.pens.hogman.network) so a lost laptop or contractor account only ever reaches the locations it is assigned to.
  • Use neutral, non-sensitive hostnames: standard public HTTPS certificates mean issued hostnames appear in public Certificate Transparency logs (names only — traffic and site contents never leave the encrypted mesh). Prefer generic operational names like cooler-1 or panel-b2 instead of customer names, street addresses, or sensitive model numbers.
  • Naming rules & rollback: each share name is a single label (lowercase letters, digits, dashes) becoming https://NAME.<pen>.pens.hogman.network. First come, first served; up to 50 names per member. If a brand-new share fails to obtain its first certificate, it tears down its server node and releases the name automatically.

Operational security checklist — what a bridge does and does not cover:

  • Keep vendor firmware updates enabled: a pen removes equipment from the public internet and restricts reachability to invited members, but it does not patch firmware vulnerabilities.
  • Change default device passwords: pen membership is a strong network perimeter, not a substitute for changing factory credentials on controllers.
  • Web interfaces only (HTTPS :443): devices that only speak raw non-HTTP protocols (such as raw Modbus, BACnet, RDP, or SSH) without a web UI are not a fit.
  • Isolated server nodes: every share runs its own embedded tsnet server identity (tag:server) with its own local CertMagic TLS keypair. Staff laptops accept zero inbound connections, and your bridge opens zero inbound firewall ports.

Listing and taking down bridges

$ ~/hogman-join share list
https://cooler-1.store-north.pens.hogman.network   http://192.168.1.40  (running in the background)

$ ~/hogman-join share stop cooler-1
✓ https://cooler-1.store-north.pens.hogman.network is down, and the name is free again.

share stop shuts down that server node and releases the hostname. Disconnecting a machine with leave stops all shares running on it first. Connected to more than one pen? Pass --pen <zone>.
