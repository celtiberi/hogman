# Security audit, November 2026

Status: **for red-team.** This audit is the gate before any P1 work.

Scope: the code on `main` at `b222045` (release `2026.11.20-b222045`), plus the live pens on hogman-1. The review was read-only, in five areas, and each area was compared with the recognised standard for it:

| Area | Standards |
|---|---|
| Join client (`core/join`, `core/join-page`) | OWASP ASVS 4.0.3 L2; TUF threat list; local-service hardening (DNS rebinding, CSRF) |
| Registrar and home page (`core/registrar`, `core/portal`) | OWASP ASVS L2 (V1–V14); OWASP CSRF and REST cheat sheets; NIST SP 800-63B for one-time secrets |
| PKI and TLS (step-ca, templates, Caddy) | RFC 5280; NIST SP 800-57; RFC 8555; Mozilla TLS (Intermediate); step-ca hardening |
| Server deployment and network policy (`deploy/`, `core/compose.yaml`, policy) | CIS Docker Benchmark; CIS Ubuntu; systemd hardening; Tailscale/Headscale ACL practice |
| Sign-up, website, supply chain | OWASP ASVS L2; OWASP Secure Headers; SLSA v1.0; OpenSSF Scorecard; GitHub Actions hardening |

Each finding below was confirmed against the code, and where marked **(live)**, against the running server.

## Verdict

The core design holds up against the standards:
- network identity is checked live against Headscale;
- the ACL denies by default;
- every pen CA is name-constrained;
- secrets go only in URL fragments, and invite tokens are hashed;
- CSRF and XSS defences are strong;
- every subprocess is run without a shell;
- backups are encrypted to a key the server never holds.

The gaps are around that core: how the pieces trust each other on the server, how processes are isolated, and the supply chain. Six items should be fixed before P1 (H1–H6).

## The certificate authority question, tested

Members install their pen's root certificate. **The worry is whether whoever controls a pen's CA could impersonate any website.** It can't, because each root carries critical X.509 name constraints. They limit it to names under the pen's zone, with all IP addresses excluded (`core/templates/root_ca.tpl`). The intermediate has the same constraints, and `hogman-join` refuses any root without them (`core/join/link.go:79-125`). Both live roots carry them **(live)**.

Tested on the Mac, with a test root constrained to `testpen.hogman`:

| Verifier | In-zone name | `www.google.com` signed by the root | `www.google.com` via a rogue **unconstrained** intermediate signed by the root |
|---|---|---|---|
| macOS trust engine (Safari, the system) | accepted | refused | refused |
| OpenSSL (curl, Linux tools) | accepted | refused | refused |
| Go `crypto/x509` | accepted | refused | refused |
| Chrome | Google's docs say constraints on installed roots have been enforced unconditionally since Chrome 126 | | |
| Firefox, Windows (CryptoAPI) | **not yet tested** (Windows support isn't shipped) | | |

One real gap here is H1: name constraints limit names, not purposes.

## Fix before P1

**H1. The root is trusted for every purpose on Windows and Linux.** (RFC 5280 §4.2.1.12; CA/B BR §7.1.2.2)
- Neither CA template has an EKU. `certutil -addstore Root` (`core/join/trust_windows.go:29`) and the Linux anchor store trust the root for all purposes.
- Name constraints don't cover a code-signing certificate with no DNS name. So a pen's CA key could sign software that a member's Windows machine trusts.
- macOS is already limited to SSL (`trust_darwin.go:41`, `-p ssl`).
- **Fix:** add `extKeyUsage: [serverAuth, clientAuth]` to both templates, make `CheckRoot` require it, and on Windows install the root for serverAuth only.
- Existing pens need a new root. There are two today, both test pens.
- This must land before Windows ships.

**H2. Any process in the pen's shared network namespace can be any member.** (ASVS V1.4, V4)
- The mesh API trusts any loopback caller's `X-Forwarded-For` (`core/registrar/http.go:438-446`).
- The portal, registrar and step-ca share core-mesh's namespace (`core/compose.yaml:93,124,143`). A compromised step-ca, for example, could act as an owner.
- **Fix:** Caddy sets a random per-boot secret header and `identify` checks it, or the API listens on a Unix socket only Caddy can read.

**H3. Hosted pens run their registrar and CA as root (live: `user=0:0`).** (CIS Docker 4.1)
- `./hogman init` records `id -u`, and `hogman-host` runs as root (`core/hogman:157`).
- **Fix:** `hogman-host add` creates a dedicated unprivileged user per pen, or a shared one. Self-hosted pens already run as the operator's user.

**H4. The sign-up broker holds the Docker socket, all of `$HOGMAN_HOME` read-write, and internet access.** (CIS Docker 5.31)
- See `deploy/hogman-host:670-680`. Breaking the page-to-broker boundary or its token means root on the host. The page itself is well isolated.
- **Fix:** run provisioning as a hardened host systemd service the page can trigger, so no container holds the socket. Failing that, put an allow-list socket proxy in front of it.

**H5. Releases aren't signed and can be built on a laptop.** (SLSA v1.0; OpenSSF Signed-Releases; TUF)
- `deploy/release.sh:32` builds locally whenever Docker is running.
- `SHA256SUMS` comes from the same origin as the files it checks (`install.sh`, `hogman-join update`).
- Anyone who can deploy the site can ship code that `install.sh` runs as root on every new server.
- **Fix now:** build only in CI (drop the local path) and add `actions/attest-build-provenance`.
- **Fix next:** the D-15 design (PR #38).

**H6. Free repository protections are off.** (OpenSSF Scorecard: Vulnerabilities, Dependency-Update-Tool, SAST, Branch-Protection)
- Secret scanning, push protection and Dependabot are disabled on a public repo **(live, `gh api`)**. There's no `govulncheck`.
- The `main` ruleset requires a PR but 0 approvals and no passing checks, so a red e2e run can still merge.
- **Fix:**
  - turn on secret scanning, push protection and Dependabot (alerts and updates for gomod, docker and actions);
  - add a `govulncheck` job;
  - require the `pen` and `shared host` checks to pass.

## Should fix (Medium)

Join client:
- **The local proxy has no client authentication.** Any process or other OS user on the computer can use it as this member (`core/join/agent.go:145,374`). The Tailscale client has the same property. Browsers can't add credentials to CONNECT, so this needs a design.
- **The one-time key is passed as a command-line argument,** so it shows in `ps` and shell history (`join-page/join.js:37-40`). Read the link from stdin.
- **The first download isn't hash-checked** in the command the join page prints. Add `shasum -a 256 -c`.

Registrar:
- **Admin invites survive their maker's demotion.** `Redeem` checks only the maker's status (`service.go:555-559`). Check the maker's current role at redemption, and revoke open invites on role change or suspension.
- **Two owners demoting each other at the same moment can leave zero owners.** `SetRole` counts and then updates without the lock (`service.go:273-279`). Use the lock and one conditional update.
- **The mesh API has no rate limit, and every request fetches Headscale's node list** (`service.go:747-756`). Add a limit per member and cache the list for a second.
- **The audit log doesn't record the device or IP,** doesn't log refused attempts, keeps going silently if a write fails, and isn't tamper-evident (`store.go:708-713`). Add attribution, log denials, hash-chain the entries and copy them off the server.

PKI:
- **Self-hosted roots are generated on the server and moved offline only by hand** (`core/hogman:168-201`), and nightly backups don't exclude `pki/offline/` (`deploy/hogman-host:485`). Both live hosted pens are clean **(live)**. Make `up`/`status` warn while the folder isn't empty, exclude it from backups, and offer generating the root on the owner's own machine.
- **The root's password sits next to its key, including in the escrow.** One age key protects every backup and every hosted root. Use a separate escrow recipient, allow hardware or plugin recipients, and tell hosted owners that the operator can rebuild their root.
- **step-ca has no issuance policy, and `http-01` is still enabled (live)** despite the 443-only design. Add an allow-list policy for `*.<zone>` that denies IPs, and set the challenges to `tls-alpn-01` only.
- **There's no way to revoke the 5-year intermediate.** Shorten it to 1–2 years, or publish a root-signed CRL.

Deployment:
- **Docker hardening is thin.** No `no-new-privileges` anywhere, `cap_drop` on two services only, no digest pins, and container logs are never rotated (a disk-fill risk).
- **Pen services listen on every interface inside the pen.** Step-ca `:9000`, DNS `:53` and the portal can be reached from the front door, which sits on every pen's network, outside the tailnet ACL. Bind them to the mesh IP.
- **The Headscale API key lasts 10 years with no rotation.** Use 90 days, rotated by the registrar.
- **Restore is never tested from a real encrypted backup.** Do it in `test-host.sh`.
- **SSH stays open to the internet until `--lock-ssh` is run by hand.** The installer should end by prompting for it.

Sign-up and site:
- **The rate limiter can be flushed** past 4096 keys or by rotating through IPv6 addresses (`web.go:266`). Key IPv6 by /64 and evict the oldest entries.
- **The waitlist has no bot check,** reveals whether an email is on it, and lets anyone remove any email.
- **No HSTS anywhere:** the site, sign-up, pens' public hosts and the portal.
- **Actions are pinned by tag, not commit SHA, and base images aren't pinned by digest.**

## Later (Low)

These go on the backlog and get fixed alongside nearby work:
- The bootstrap ACL still lists port 80. Grants use `ip` instead of `tcp:`.
- `trusted_proxies` trusts all of RFC 1918. `REVIEW.md` claims `trusted_proxies_strict`, which isn't configured.
- Commands run under sudo are looked up on the `PATH`.
- `systemdQuote` doesn't escape `%`/`$`.
- `share` doesn't validate `me.Network`.
- Link `t`/`k` parameters aren't charset-checked in Go.
- Background processes are stopped by PID with no identity check.
- Folder shares serve dotfiles and directory listings.
- Suspend/Kick have a small race.
- Admins have no invite cap, and the maximum invite TTL is 30 days.
- `backup-allow` accepts a key comment with a newline. The backup staging folder isn't cleaned up on failure.
- The backup service unit has no systemd hardening.
- The sign-up result is readable for 24 hours, and sign-up HTTP servers have no idle timeout.
- Missing Permissions-Policy, COOP and nosniff on `/join/dl` and `/hogman/*`.

## Accepted, by decision

- **Device keys aren't bound to hardware.** A copied state folder works elsewhere until the device is removed. Phase 2 (D-13, D-14); the FAQ says so.
- **No account recovery** (D-12, D-16, D-17).
- **First install is trust-on-first-use over HTTPS** (D-15 design).

## Kept: these already meet the standard

- **Identity:** the live Headscale node ID is checked on every request, re-synced once on a mismatch, and fails closed.
- **Network policy:** default-deny ACL from first boot; members reach servers on 443 only; `tagOwners` empty; private DERP relay with `verify_clients`.
- **Secrets:** invite tokens are 256-bit, stored hashed and single-use under a lock. Device keys are never stored and last an hour. Secrets travel only in URL fragments, with `no-store`.
- **Web defences:** CSRF in three layers (Sec-Fetch-Site, exact Origin, JSON only) that handles `.hogman` sibling sites correctly. `textContent`-only DOM and a strict CSP.
- **Input handling:** parameterised SQL everywhere; strict JSON with size caps; every subprocess run without a shell; regex-validated names before they become paths.
- **PKI:** name-constrained root and intermediate (tested above); root pinned by fingerprint from the link; 7-day leaf certificates; macOS trust limited to SSL.
- **The local agent:** loopback Host allow-list (no DNS rebinding); proxy reaches only pen devices on 443.
- **Backups:** age-encrypted to an offline key, pulled over a restricted SSH account. Hosted roots are escrowed and deleted from the server.
- **Sign-up:** page and broker split cleanly. The page runs read-only, non-root, with every capability dropped.
- **CI:** read-only workflow token, no `pull_request_target`, no secrets in workflows.
